\title{CloudSentinel AI: A Context-Aware Framework for Cloud Misconfiguration Risk Assessment and Candidate Attack-Path Analysis}

\author{\IEEEauthorblockN{Harshith}}

\begin{document}
\maketitle

\begin{abstract}
Enterprise cloud infrastructures routinely suffer from finding fatigue, where thousands of isolated resource alerts generated by standard auditing suites obscure actual threat exposure. This paper introduces CloudSentinel AI, an AWS-focused architecture engineered to shift cloud posture analysis from disjointed resource checklists to relationship-aware graph reasoning. Our design ingests read-only configuration metadata across compute, storage, identity, and network boundaries, mapping assets and dependencies into a typed security knowledge graph. Rather than assuming theoretical connectivity equates to real-world compromise, our candidate attack-path engine enforces strict precondition validation before asserting multi-hop traversal sequences. We formulate an interpretable, four-factor scoring heuristic that balances finding severity against topological path context, external network reachability, and asset business value. To streamline analyst triage without introducing generative hallucinations, our reporting workflow binds Large Language Models behind deterministic configuration facts and mandatory human review. We validate the framework's core assumptions against a verified, non-production AWS baseline deployed in the \texttt{ap-south-2} region. Preliminary read-only scans successfully flagged an open security-group rule and a scoped IAM wildcard while correctly refusing to assert candidate attack paths due to missing network interfaces, absent Internet routes, and active account-level S3 protections. We establish an empirical evaluation protocol across six representative cloud scenarios, demonstrating bounded evidence capture and defensive precondition rejection.
\end{abstract}

\begin{IEEEkeywords}
cloud security, cloud misconfiguration, AWS, knowledge graph, attack-path analysis, risk prioritisation, LLM-assisted security reporting

\section{Introduction}
Modern software engineering has largely abandoned on-premises perimeters in favor of software-defined, multi-tenant cloud ecosystems \cite{nist2011cloud}. While on-demand resource provisioning delivers immense elasticity, it also relocates the operational attack surface to an interconnected fabric of identity policies, network boundaries, and storage permissions \cite{alouffi2021cloudsecurity,kumar2019cloudsecurity}. In these environments, security posture is not an intrinsic property of an isolated asset. Instead, risk emerges from transitive relationships among loosely coupled cloud services \cite{torkura2021multicloud,saxena2021multicloud}.

Industry incident retrospectives show that cloud breaches rarely originate from zero-day binary exploitation. Rather, real-world failures are driven by mundane administrative oversights, overly permissive Identity and Access Management (IAM) permissions, and configuration flaws embedded in Infrastructure-as-Code (IaC) deployment definitions \cite{liu2024misconfigurations,rahman2019icsesmells}. Contemporary Cloud Security Posture Management (CSPM) suites evaluate cloud tenancies by matching individual resources against static compliance benchmarks. This paradigm generates vast volumes of atomized alerts, leaving security operations centers (SOC) overwhelmed by warning fatigue \cite{vanede2022iam}. An isolated finding carries little diagnostic value without its operational environment: an open ingress rule on an Amazon EC2 security group represents negligible practical risk if the instance resides in an unrouted private subnet, whereas an identical rule attached to an Internet-facing host with broad assume-role capabilities constitutes an immediate escalation path.

To bridge this contextual void, we present CloudSentinel AI, an AWS-targeted framework that unifies multi-service metadata extraction with relationship-aware graph analytics. Rooted in the Design Science Research (DSR) paradigm \cite{hevner2004design}, our work treats the proposed framework as an engineering artifact evaluated against clear operational bounds. Specifically, this paper contributes:
\begin{enumerate}
\item A multi-service AWS ontology and graph schema that models compute, storage, identity, and network resources as typed nodes and inter-service dependencies as directed edges.
\item A candidate attack-path discovery engine that enumerates bounded traversal chains while discarding paths lacking verified runtime preconditions.
\item A linear, fully explainable risk scoring heuristic that quantifies exposure from raw severity, asset criticality, candidate-path context, and network accessibility.
\item An evidence-bound LLM reporting contract that generates human-reviewed triage summaries strictly constrained to collected configuration evidence.
\end{enumerate}

Importantly, we present CloudSentinel AI as a formal design and validation protocol. We deliberately avoid asserting premature production superiority or general detection claims ahead of controlled benchmark execution.

\section{Background and Related Work}

\subsection{Cloud Misconfiguration Detection and IaC Verification}
Configuration defects are widely acknowledged as the predominant operational hazard across public cloud tenancies \cite{liu2024misconfigurations}. A rich body of research focuses on shifting security left by analyzing declarative deployment templates prior to provisioning. Rahman et al.~\cite{rahman2019icsesmells} cataloged seven recurring security smells in IaC scripts, showing that hardcoded credentials and excessive privileges regularly bypass code review. Chiari et al.~\cite{chiari2022iacsurvey} surveyed static analysis methodologies for IaC, contrasting pre-deployment syntax validation against the realities of live cloud drift. In container ecosystems, empirical studies by Bose et al.~\cite{bose2021kubernetes} and Rahman et al.~\cite{rahman2023k8smisconfig} identified recurring RBAC misconfigurations and unsegmented pod networks within open-source Kubernetes manifests.

At the storage layer, public object exposures represent an ongoing vulnerability. Olorunlana~\cite{olorunlana2026s3} introduced an automated policy-enforcement framework to block insecure Amazon S3 bucket configurations directly within deployment templates. However, static linters cannot observe post-deployment drift, dynamic trust relationships, or cross-service interactions in active enterprise accounts. Addressing this gap, Torkura et al.~\cite{torkura2021multicloud} proposed continuous auditing architectures for multi-cloud setups, emphasizing real-time telemetry analysis. In parallel, van Ede et al.~\cite{vanede2022iam} utilized anomaly detection to spot risky permission combinations in AWS IAM policies. Yet, analyzing identity definitions in isolation from network topologies fails to reveal whether an overly permissive principal is practically reachable by an attacker.

\subsection{Graph-Based Modeling and Attack-Path Analysis}
Knowledge graphs provide a robust mathematical abstraction for representing heterogeneous entities and complex inter-resource relationships \cite{hogan2021knowledge}. In network security, graph structures have long underpinned vulnerability analysis. Phillips and Swiler~\cite{phillips1998graph} pioneered graph-based vulnerability assessment, laying the groundwork for algorithmic attack-graph generation. Sheyner et al.~\cite{sheyner2002automated} formalized attack-graph derivation using model checking, while Jha et al.~\cite{jha2002formal} applied formal cut-set logic to identify optimal remediation points.

Adapting these concepts to cloud fabrics requires addressing dynamic virtualization, transient workloads, and identity-based perimeters. Sabur et al.~\cite{sabur2022scalable} tackled combinatorial state-space growth in cloud networks through modular graph decomposition. Elmiger et al.~\cite{elmiger2023attackpaths} demonstrated the power of graph analytics in enterprise Microsoft tenants, identifying privilege-escalation routes that bypassed standard audit rules. In audit telemetry, Kurniawan et al.~\cite{kurniawan2022krystal} introduced KRYSTAL, combining knowledge graphs with tactical attack pattern mapping. While these contributions confirm the value of graph models, they often presume that topological connectivity directly implies exploitability. CloudSentinel AI enforces a strict distinction: every graph transition is treated merely as a hypothesis until verified against explicit reachability and identity preconditions.

\subsection{Machine Learning, Explainable AI, and Large Language Models}
Machine learning methods have been extensively investigated for cloud anomaly detection and intrusion classification, as synthesized by Nassif et al.~\cite{nassif2021mlcloudsecurity}. Nonetheless, deep black-box architectures offer little interpretability, preventing security teams from understanding the root cause of an alert. Explainable Artificial Intelligence (XAI) has thus become essential in security operations \cite{rjoub2023xai}. Charmet et al.~\cite{charmet2022xai} highlighted that without transparent attribution, analysts struggle to justify high-impact remediation decisions. Model-agnostic explainability frameworks like LIME~\cite{ribeiro2016lime} and SHAP~\cite{lundberg2017shap} underscore the necessity of transparent feature attribution, a principle we mirror by adopting an additive, inspectable scoring model.

Simultaneously, Large Language Models (LLMs) built upon Transformer architectures \cite{vaswani2017attention} have revealed remarkable zero- and few-shot reasoning capabilities \cite{brown2020language}, with systems such as GPT-4 \cite{openai2023gpt4} demonstrating proficiency in distilling complex technical records. In a systematic review, Xu et al.~\cite{xu2024llmcybersecurity} surveyed LLM utility across cyber defense, identifying strong potential in log synthesis and remediation guidance. However, unconstrained LLMs exhibit dangerous tendencies toward factual hallucination and invalid security advice \cite{xu2024llmcybersecurity}. CloudSentinel AI mitigates this liability by confining the language model to an advisory role, strictly bounded by structured evidence and human sign-off.

\subsection{Problem Formulation and Research Gaps}
Our literature analysis identifies three unresolved deficiencies:
\begin{enumerate}
\item Contemporary CSPMs evaluate resources as isolated silos, failing to track multi-stage traversal risks.
\item Theoretical cloud attack-graph models often omit operational preconditions, generating unrealistic lateral movement paths.
\item Emerging LLM security tools lack deterministic ground-truth gating, introducing generative hallucinations into remediation workflows.
\end{enumerate}
CloudSentinel AI directly tackles these limitations through a hybrid architecture combining deterministic rule verification, precondition-gated graph traversals, inspectable risk scoring, and evidence-locked LLM reporting.

\section{Proposed Framework}

\subsection{Scope and Threat Model}
CloudSentinel AI targets core infrastructure services within an AWS tenancy: Amazon EC2, Amazon S3, AWS IAM, Amazon VPC (including security groups and route tables), Amazon RDS, AWS Secrets Manager, and AWS CloudTrail. The system operates strictly via read-only AWS API credentials, collecting only accessible configuration metadata.

We define an attacker model initiated at an explicit entry condition, such as an unauthenticated external network boundary or an assumed testing principal. Attack transitions are permitted solely when substantiated by collected configuration metadata. The engine never presumes exploit availability, zero-day vulnerabilities, or unverified credential theft; every transition edge demands recorded and verifiable preconditions.

\subsection{Architecture and Graph Schema}
The processing pipeline executes through five modular phases:
\begin{itemize}
\item \textbf{Metadata Collection:} Gathers configuration snapshots from target AWS services via paginated read-only APIs.
\item \textbf{Rule Evaluation:} Evaluates deterministic security rules adapted from established benchmarks (e.g., CIS AWS Foundations).
\item \textbf{Knowledge Graph Synthesis:} Translates raw metadata and findings into a typed property graph representing assets, policies, and network attachments.
\item \textbf{Candidate-Path Engine:} Traverses the graph from documented entry nodes to sensitive resources, filtering out paths with unfulfilled preconditions.
\item \textbf{Advisory Reporting:} Synthesizes path evidence and prioritization metrics into structured, human-reviewed incident briefs.
\end{itemize}

\subsection{Candidate-Path Analysis and Prioritisation}
A graph edge represents an observable relationship or permission grant; it does not constitute proof of active compromise \cite{sheyner2002automated,sabur2022scalable}. We define a candidate path as an acyclic, evidence-backed chain connecting an entry point to a high-value asset \cite{elmiger2023attackpaths}. To avoid combinatorial explosion in large cloud environments, the search engine enforces a maximum traversal depth $d$ and retains at most $k$ candidate paths per target. Paths missing requisite preconditions (such as unroutable subnets or absent instance profiles) are discarded during traversal.

To eliminate the opacity of black-box risk algorithms \cite{ribeiro2016lime,lundberg2017shap}, we compute asset risk via an inspectable linear heuristic:
\begin{equation}
R = \alpha S + \beta C + \gamma P + \delta E,
\label{eq:risk}
\end{equation}
where all variables are normalized to $[0,1]$:
\begin{itemize}
\item $S$: Raw finding severity assigned by evaluated benchmark rules.
\item $C$: Criticality score reflecting data sensitivity and business role.
\item $P$: Path metric reflecting the existence and length of verified candidate paths.
\item $E$: Exposure metric capturing public routability and ingress accessibility.
\end{itemize}
The weighting parameters satisfy $\alpha + \beta + \gamma + \delta = 1$ and are frozen prior to evaluation. Exposure $E$ is isolated from $C$ to avoid double-counting external exposure in asset valuation. $R$ serves as a comparative prioritization index rather than an empirical probability of breach.

\subsection{LLM-Assisted Reporting Contract}
The reporting interface accepts only validated configuration facts, graph paths, and rule metadata. The generative prompt explicitly instructs the model to:
\begin{enumerate}
\item Separate confirmed facts from hypothetical attacker actions.
\item List missing preconditions that prevent path completion.
\item Map every remediation action to a specific rule finding.
\item Insert an explicit disclaimer stating human review is required.
\end{enumerate}
Because prompt constraints cannot guarantee complete avoidance of hallucination \cite{xu2024llmcybersecurity,openai2023gpt4}, LLM outputs remain purely advisory and are barred from directly executing remediation commands. Table~\ref{tab:claims} details the claim-to-evidence validation map.

\subsection{Ground Truth and Units of Analysis}
To eliminate ambiguity during scoring, we establish three distinct analysis units:
\begin{itemize}
\item \textbf{Finding:} A discrete rule violation linked to an individual cloud resource.
\item \textbf{Candidate Path:} An ordered sequence of evidence-backed graph edges connecting an entry condition to a target asset.
\item \textbf{Consolidated Alert:} A grouped cluster of co-located findings associated with a common workload or path context.
\end{itemize}
Prior to each assessment run, a formal scenario catalogue (Table~\ref{tab:scenarios}) records the intended configuration, expected findings, negative controls, and permitted remediation steps. This catalogue serves as the baseline ground truth, frozen and independently reviewed prior to execution \cite{liu2024misconfigurations,rahman2023k8smisconfig}.

\subsection{Metrics and Path Review}
Detection performance is benchmarked strictly against the scenario ground truth using standard classification metrics:
\begin{equation}
\begin{aligned}
\mathrm{Precision}&=\frac{TP}{TP+FP},\\
\mathrm{Recall}&=\frac{TP}{TP+FN},\\
F1&=\frac{2TP}{2TP+FP+FN},
\end{aligned}
\label{eq:metrics}
\end{equation}
alongside the false positive rate $FPR = FP / (FP + TN)$ where negative control fixtures establish true negatives ($TN$).

Candidate paths are evaluated under three criteria:
\begin{enumerate}
\item \textbf{Exact Match:} The sequence of traversed nodes, edge permissions, entry conditions, and target assets matches the ground-truth specification.
\item \textbf{Partial Match:} The discovered chain represents a valid sub-path or superset, with divergences explicitly documented.
\item \textbf{Invalid Path:} The chain introduces unverified transitions, absent permissions, or missing preconditions.
\end{enumerate}
Alert deduplication is measured as the ratio of consolidated alert clusters to raw baseline findings. These metrics are tracked independently and never combined into misleading composite scores.

\subsection{Execution Protocol and Reproducibility}
Every evaluation run archives pre-scan configuration snapshots, resource inventories, execution logs, raw JSON tool outputs, graph exports, and post-experiment teardown receipts. Comparative benchmarks against baseline tools enforce identical account scopes, IAM role permissions, and assessment windows. Non-warm-up runs are repeated at least three times to report latency distributions across scanning and graph-generation phases. An in-memory fixture runner validates catalogue integrity prior to AWS API execution; fixture results are treated as unit tests and excluded from cloud benchmark statistics.

\subsection{LLM-Report Review Rubric}
Each generated report undergoes blind evaluation by at least two independent security reviewers across four dimensions:
\begin{itemize}
\item \textbf{Evidence Consistency:} Absence of unsupported claims or unverified assumptions.
\item \textbf{Technical Accuracy:} Correct identification of AWS service semantics and IAM policy behaviors.
\item \textbf{Clarity:} Concise, structured presentation suitable for incident response triage.
\item \textbf{Actionability:} Practical, safe remediation advice free of destructive commands.
\end{itemize}
Reviewers score each category on a predefined 1--5 scale, with inter-rater agreement measured via Cohen's kappa.

\subsection{Research Questions}
The evaluation addresses four targeted questions:
\begin{itemize}
\item \textbf{RQ1 (Detection):} Does the rule analyzer reliably identify labelled findings across S1--S6 with zero false positives on negative controls?
\item \textbf{RQ2 (Path Validity):} Do generated candidate paths satisfy expected precondition constraints without asserting phantom traversals?
\item \textbf{RQ3 (Prioritization):} Does the linear scoring formula $R$ correlate with expert reference rankings under sensitivity analysis?
\item \textbf{RQ4 (Report Fidelity):} Do LLM-assisted summaries adhere to the evidence boundary without introducing hallucinations or unsafe commands?
\end{itemize}

Read-only API verification confirmed this baseline state, with subsequent Terraform execution plans showing zero pending modifications. Initial collection passes generated one medium-severity finding for an ingress rule permitting \texttt{tcp/8443} from \texttt{0.0.0.0/0}. Crucially, the engine rejected asserting an attack path: the necessary reachability preconditions—an attached Internet Gateway, an external route table entry, and an active network interface—were entirely absent.

In a secondary test pass reflecting S1/S2 conditions, bucket public-access blocks were temporarily lifted and an inline \texttt{s3:*} policy was attached to the test role. The evaluator detected both high-severity configuration anomalies but still correctly refused to generate an external attack path. In this instance, an account-level S3 Block Public Access setting intervened to block the public bucket policy, demonstrating defense-in-depth enforcement. For S4, a dedicated CloudTrail trail was deployed in a stopped state (\texttt{IsLogging = false}); the collector detected the missing audit trail without disrupting account-level logging. During the temporary S5 run, the engine observed the instance profile's read privilege toward the synthetic bucket while confirming the absence of a public IPv4 address, lack of Internet routing, IMDSv2 enforcement (hop limit 1), and denial of \texttt{secretsmanager:GetSecretValue}. Consequently, no compromise path was asserted. A deterministic local S6 model similarly rejected hypothetical SSRF paths in the absence of IMDSv1 or external egress. These results validate our precondition-filtering mechanics on live AWS infrastructure, while comparative benchmark trials remain planned future work.

\section{Discussion and Limitations}
Our experimental findings reinforce that topological graph reachability must not be confused with true exploitability. Threat models, policy evaluation semantics, and traversal constraints must be explicitly formalized. Furthermore, our synthetic test scenarios do not encompass the full architectural diversity of enterprise multi-account environments \cite{liu2024misconfigurations,rahman2019icsesmells}. Expanding graph analytics beyond AWS to multi-cloud ecosystems \cite{torkura2021multicloud,saxena2021multicloud} requires unifying divergent provider permission semantics and entity models. In-memory graph engines also risk performance degradation in tenants containing millions of cloud assets, necessitating future research into distributed graph indexing \cite{sabur2022scalable}.

Finally, deploying LLMs in cybersecurity workflows introduces latency, cost, and data governance considerations. Sensitive cloud resource identifiers and credential names must be sanitized prior to model ingestion, and generative output must never trigger autonomous remediation without human verification.

\section{Conclusion}
This paper presented CloudSentinel AI, an AWS security framework designed to transition cloud misconfiguration analysis from isolated compliance audits to context-aware attack-path reasoning. By combining metadata collection, precondition-gated graph traversals, an explainable scoring heuristic, and evidence-locked LLM reporting, the framework targets the root causes of alert fatigue. Baseline tests on active AWS infrastructure confirm the framework's ability to capture verified configuration evidence and eliminate phantom attack paths. Future work will center on executing the full S1--S6 benchmark protocol, benchmarking detection against commercial CSPM baselines, and scaling the graph engine across multi-account cloud fabrics.
