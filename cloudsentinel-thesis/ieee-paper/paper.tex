\title{CloudSentinel AI: A Context-Aware Framework for Cloud Misconfiguration Risk Assessment and Candidate Attack-Path Analysis}

\author{\IEEEauthorblockN{Harshith}}

\begin{document}
\maketitle

\begin{abstract}
Cloud Security Posture Management (CSPM) tools commonly report findings at the individual-resource level, which can obscure relationships among cloud assets and complicate remediation prioritisation. This paper proposes CloudSentinel AI, an AWS-focused framework for context-aware cloud misconfiguration assessment. The design collects selected configuration metadata, models assets and relationships in a knowledge graph, evaluates documented security rules, and derives candidate attack paths subject to explicit preconditions. A transparent contextual scoring heuristic is proposed to prioritise findings using asset criticality, exposure, identity permissions, data sensitivity, and graph context. An LLM-assisted reporting component is constrained to evidence-bounded, human-reviewed explanations and remediation recommendations. The paper also defines a controlled AWS evaluation protocol based on labelled scenarios. A tagged, isolated AWS baseline has been deployed, while a private S5 workload was temporarily deployed, configuration-verified, assessed by read-only evidence-collection passes, and then torn down. The passes detected a bounded security-group configuration finding and a temporary bucket-scoped IAM wildcard permission, while rejecting candidate paths whose reachability preconditions were absent. A private S5 instance-profile relationship to a synthetic S3 object and metadata-only secret was observed, but no candidate path was asserted. An account-level S3 safeguard blocked attachment of the planned empty-bucket public policy. A dedicated S4 CloudTrail test trail was also observed in the disabled state without altering an existing trail. A deterministic local S6 precondition model also rejected the hypothetical SSRF-to-IAM path without contacting AWS or a network; no S6 service was deployed. Comparative scenario-level experiments remain unexecuted. This work therefore does not claim completed experimental validation or general production effectiveness.
\end{abstract}

cloud security, cloud misconfiguration, AWS, knowledge graph, attack-path analysis, risk prioritisation, LLM-assisted security reporting

\section{Introduction}
Cloud computing provides on-demand access to configurable computing resources over standard network protocols \cite{nist2011cloud}, transforming enterprise infrastructure through rapid resource provisioning and multi-tenant resource pooling. However, the shared responsibility model and dynamic orchestration intrinsic to modern cloud architectures introduce substantial security challenges \cite{alouffi2021cloudsecurity,kumar2019cloudsecurity}. Security posture in cloud environments does not depend solely on individual asset configurations; rather, it emerges from the intricate interactions among identity controls, network routing boundaries, object storage access policies, audit logging, and interdependent service relationships \cite{torkura2021multicloud,saxena2021multicloud}.

Unlike conventional software vulnerabilities resulting from source-code programming errors, cloud security incidents predominantly stem from security misconfigurations, overly permissive identity privileges, and defective Infrastructure-as-Code (IaC) deployment definitions \cite{liu2024misconfigurations,rahman2019icsesmells}. Contemporary Cloud Security Posture Management (CSPM) tools typically assess cloud accounts by scanning isolated assets against static compliance rules. While effective at cataloguing individual compliance violations, this resource-centric paradigm produces thousands of atomised alerts that obscure underlying architectural relationships \cite{vanede2022iam}. An isolated configuration finding does not convey its operational significance without contextual grounding: for example, the practical risk posed by an open security-group ingress rule depends fundamentally on whether the associated workload is publicly routable, what IAM role is attached, which sensitive data stores are reachable, and what defensive controls remain active along potential traversal paths.

CloudSentinel AI is proposed as an AWS-focused research framework that combines multi-service configuration assessment with relationship-aware reasoning. The study follows a Design Science Research (DSR) methodology in which the framework serves as the purposeful artifact and the controlled evaluation protocol empirically tests its bounded claims \cite{hevner2004design}. The primary contributions of this paper are:
\begin{enumerate}
\item A typed AWS resource-and-relationship model for building a security knowledge graph from configuration metadata across EC2, IAM, S3, VPC, RDS, Secrets Manager, and CloudTrail.
\item A candidate attack-path analysis algorithm that enumerates bounded, evidence-supported traversal sequences while strictly validating explicit reachability and privilege preconditions.
\item A transparent contextual risk prioritisation heuristic that scores findings using documented severity, asset criticality, attack-path context, and network exposure without black-box opacity.
\item An evidence-bounded LLM-assisted reporting contract that generates human-reviewed explanations and advisory remediation guidance grounded exclusively in verified configuration facts.
\end{enumerate}

The framework is a design proposal. Any empirical claim of superior finding detection, alert deduplication, or analyst efficiency requires the controlled evaluation design formalized in this paper.

\section{Background and Related Work}

\subsection{Cloud Misconfiguration Detection and IaC Verification}
Configuration errors represent a leading operational risk across public cloud infrastructures \cite{liu2024misconfigurations}. A substantial body of literature addresses static configuration verification in Infrastructure-as-Code (IaC) templates prior to deployment. Rahman et al.~\cite{rahman2019icsesmells} categorized recurring security smells in IaC scripts, demonstrating that hardcoded secrets and unconstrained administrative privileges frequently escape code review. Chiari et al.~\cite{chiari2022iacsurvey} provided a comprehensive survey of static analysis techniques for IaC, highlighting the trade-offs between pre-deployment policy validation and post-deployment runtime verification. In containerized cloud deployments, Bose et al.~\cite{bose2021kubernetes} and Rahman et al.~\cite{rahman2023k8smisconfig} conducted empirical investigations of security misconfigurations in Kubernetes manifests, documenting widespread authorization flaws and insecure network policies.

In the storage domain, Amazon S3 bucket exposures remain a frequent source of enterprise data breaches. Olorunlana~\cite{olorunlana2026s3} introduced a policy-enforced framework for preventing Amazon S3 cloud storage misconfigurations using Infrastructure-as-Code validation, emphasizing automated policy enforcement to block unintentional public exposures. However, pre-deployment static analysis alone cannot detect configuration drift, dynamic privilege assumptions, or multi-resource interactions arising in active cloud tenancies. To address operational drift, Torkura et al.~\cite{torkura2021multicloud} proposed continuous auditing and threat detection architectures across multi-cloud environments. Similarly, van Ede et al.~\cite{vanede2022iam} developed anomaly detection techniques to identify anomalous misconfigurations within AWS Identity and Access Management (IAM) policies, underscoring the necessity of policy reasoning over complex identity structures.

\subsection{Graph-Based Modeling and Attack-Path Analysis}
Knowledge graphs provide a flexible, formal representation for capturing entities, attributes, and multi-relational dependencies \cite{hogan2021knowledge}. In cybersecurity, graph representations have long been leveraged to model networked systems and potential exploitation sequences. Foundational work by Phillips and Swiler~\cite{phillips1998graph} introduced graph-based network vulnerability analysis, establishing the conceptual basis for modern attack graphs. Sheyner et al.~\cite{sheyner2002automated} formulated automated generation and analysis of attack graphs using model-checking techniques, while Jha et al.~\cite{jha2002formal} provided formal analyses to determine minimal cut-sets and vulnerability minimization strategies.

In cloud computing environments, attack-graph methods have evolved to accommodate dynamic virtualization and cloud-native identities. Sabur et al.~\cite{sabur2022scalable} proposed scalable graph-based security analysis frameworks tailored for cloud networks, addressing combinatorial state-space explosion through modular graph partitioning. Elmiger et al.~\cite{elmiger2023attackpaths} demonstrated the practical utility of graph reasoning for discovering critical attack paths within Microsoft cloud tenant environments, revealing multi-hop traversal risks that isolated security checks failed to surface. Extending graph reasoning to audit telemetry, Kurniawan et al.~\cite{kurniawan2022krystal} proposed KRYSTAL, a knowledge graph-based framework for tactical attack discovery in audit logs. While these approaches motivate graph-based security reasoning, they frequently treat topological reachability as equivalent to exploitability. CloudSentinel AI distinguishes structural graph connectivity from verified attack paths by demanding that every edge transition satisfy explicit, recorded preconditions.

\subsection{Machine Learning, Explainable AI, and Large Language Models}
Machine learning techniques have been widely explored for cloud threat detection, anomaly classification, and security log analysis, as surveyed by Nassif et al.~\cite{nassif2021mlcloudsecurity}. However, complex machine learning classifiers frequently operate as black boxes, providing predictions without interpretable explanations. To overcome this limitation, Explainable Artificial Intelligence (XAI) has emerged as an essential discipline in cybersecurity \cite{rjoub2023xai}. Charmet et al.~\cite{charmet2022xai} examined XAI literature in cybersecurity, emphasizing that security analysts require transparent rationales to justify incident triage and remediation decisions. Foundational model-agnostic explanation techniques such as LIME~\cite{ribeiro2016lime} and SHAP~\cite{lundberg2017shap} demonstrate the importance of local feature attribution and transparent scoring components.

Concurrently, generative Large Language Models (LLMs) founded on the Transformer architecture~\cite{vaswani2017attention} have demonstrated strong few-shot reasoning capabilities across diverse tasks \cite{brown2020language}, with advanced systems such as GPT-4~\cite{openai2023gpt4} demonstrating proficiency in technical summarization and code generation. Xu et al.~\cite{xu2024llmcybersecurity} provided a systematic literature review of LLMs in cybersecurity, detailing applications in vulnerability explanation, log triage, and remediation advice. Nevertheless, LLMs exhibit well-documented propensities for hallucination, unsupported factual assertion, and hazardous remediation recommendations when unconstrained \cite{xu2024llmcybersecurity}.

\subsection{Research Gaps and Proposed Approach}
Existing literature reveals three principal research gaps: (i) CSPM tools and static IaC scanners evaluate isolated resources without modeling inter-resource relationship chains; (ii) traditional attack-graph approaches often presume reachability without validating cloud-specific runtime preconditions; and (iii) emerging AI and LLM security tools lack deterministic evidence bounding, risking hallucinations in mission-critical remediation. CloudSentinel AI directly bridges these gaps by synthesizing multi-service AWS configuration analysis, precondition-guarded candidate-path discovery, transparent contextual prioritisation, and an evidence-bounded LLM reporting contract within a reproducible evaluation methodology.

\section{Proposed Framework}

\subsection{Scope and Threat Model}
The initial scope of CloudSentinel AI encompasses an AWS account containing EC2, S3, IAM, VPC/security-group, RDS, Secrets Manager, and CloudTrail configuration metadata. The framework operates under read-only collection credentials, evaluating solely the resources visible under authorized API queries. The threat model begins with an external or authenticated actor situated at a documented entry condition (e.g., a public network interface or compromised test principal) and admits transitions only when fully supported by collected configuration evidence. It does not assert an initial compromise, credential theft, exploit availability, or successful lateral movement unless those preconditions are explicitly represented, verified against metadata, and independently reviewed.

\subsection{Architecture and Graph Schema}
The proposed processing pipeline consists of five sequential stages. First, an asset collector retrieves versioned AWS configuration metadata using read-only APIs. Second, a configuration analyzer evaluates versioned deterministic rules derived from established industry benchmarks. Third, a graph builder constructs typed nodes and directed edges representing cloud assets, configuration findings, and architectural dependencies. Fourth, a candidate-path engine searches the graph under the specified threat model. Finally, an LLM-assisted reporting component compiles findings, path evidence, scoring rationale, and advisory remediation guidance. \subsection{Candidate-Path Analysis and Prioritisation}
A graph edge represents a documented relationship or security-relevant condition; it does not independently prove exploitability \cite{sheyner2002automated,sabur2022scalable}. A candidate path is a bounded, loop-free sequence from a documented entry condition to a target asset \cite{elmiger2023attackpaths}. The engine will enumerate at most $k$ paths with a maximum depth $d$, reject paths with a missing required precondition, and retain evidence for every edge. It therefore performs bounded candidate-path discovery rather than claiming exhaustive enumeration of all attack paths.

To provide transparent risk scoring aligned with interpretability principles \cite{ribeiro2016lime,lundberg2017shap}, the proposed prioritisation score is formulated as a linear combination of normalized factors:
\begin{equation}
R = \alpha S + \beta C + \gamma P + \delta E,
\label{eq:risk}
\end{equation}
where all components are normalized to $[0,1]$: $S$ is documented finding severity, $C$ is asset criticality, $P$ is evidence-supported candidate-path context, and $E$ is externally reachable exposure. The non-negative weights satisfy $\alpha + \beta + \gamma + \delta = 1$ and will be fixed before evaluation. Exposure is excluded from $C$ to prevent double counting. $R$ is a deterministic prioritisation score, not an estimated probability of compromise; sensitivity analysis will report how ranking shifts under alternative weighting schemes.

\subsection{LLM-Assisted Reporting Contract}
The reporting component receives only approved, evidence-bounded findings, graph relationships, and remediation context. Each generated report must distinguish observed evidence from assumptions, identify missing preconditions, link each recommendation to relevant findings, and state that human review is required. Prompt engineering cannot guarantee factual accuracy or eliminate hallucinations \cite{xu2024llmcybersecurity,openai2023gpt4}; the component is advisory and will be evaluated for evidence consistency, technical accuracy, clarity, and actionability. It must not automatically execute remediation or receive unapproved sensitive data. Table~\ref{tab:claims} summarizes the claim-to-evidence evaluation mapping.

\section{Controlled Evaluation Design}
The proposed evaluation uses an isolated, authorized, non-production AWS account. All resources will be tagged, synthetic or non-sensitive data will be used, least-privilege roles and budget alarms will be configured, and every scenario will have a verified cleanup record. Intentionally weak configurations will remain within the defined laboratory boundary and will not be exposed to the public Internet, adhering to established design-science evaluation principles \cite{hevner2004design}.

\subsection{Ground Truth and Units of Analysis}
The evaluation distinguishes three units. A \emph{finding} is one rule violation attached to a resource. A \emph{candidate path} is an ordered graph sequence with documented preconditions. A \emph{consolidated alert} groups related findings for a shared path or asset context. Before each run, a scenario catalogue (Table~\ref{tab:scenarios}) records the intentional configuration state, expected findings, negative controls, expected and forbidden candidate paths, severity rationale, and permitted remediation guidance. This catalogue forms the ground truth; it must be frozen before scanning and independently reviewed \cite{liu2024misconfigurations,rahman2023k8smisconfig}.

\subsection{Metrics and Path Review}
Finding-level precision, recall, F1, and false-positive rate are computed only against the labelled scenario finding set:
\begin{equation}
\begin{aligned}
\mathrm{Precision}&=\frac{TP}{TP+FP},\\
\mathrm{Recall}&=\frac{TP}{TP+FN},\\
F1&=\frac{2TP}{2TP+FP+FN}.
\end{aligned}
\label{eq:metrics}
\end{equation}
The false-positive rate is $FP/(FP+TN)$ when negative controls define $TN$. A candidate path is an \emph{exact match} when its entry condition, ordered evidence-backed edges, target, and required preconditions match the catalogue; it is a \emph{partial match} when it represents a valid subset or superset with the difference stated; otherwise it is \emph{invalid}. Prioritisation quality will be measured against a pre-specified reference ranking, while alert reduction will be reported as consolidated alerts divided by normalised baseline findings for the same scenario. These measures must not be aggregated across units of analysis.

\subsection{Execution and Baseline Protocol}
For every scenario, the study will archive the pre-scan configuration snapshot, resource inventory, ground-truth catalogue, tool version, enabled checks, account scope, permissions, execution time, raw output, graph export, candidate-path evidence, and cleanup record. CloudSentinel and selected baselines will use the same account scope, permissions, configuration, and execution date. Findings will be normalised to the defined finding unit before comparison. Each timing measurement will use at least three non-warm-up repetitions and report the timing boundary, median, range, failures, host specification, AWS region, and any external API latency. A local in-memory fixture runner validates catalogue handling and attack-graph integration before cloud deployment; its outputs are regression checks and are excluded from all cloud-performance and accuracy metrics. Capability matrices based on vendor documentation will be labelled as documentation-based feature comparisons, not benchmark performance results.

\subsection{LLM-Report Review}
Each LLM-assisted report will be evaluated by at least two independent reviewers using a pre-defined rubric. The rubric scores: (i) evidence consistency, (ii) technical accuracy, (iii) clarity, and (iv) actionability. Reviewers will mark unsupported statements and unsafe recommendations separately, report agreement before adjudication, and retain the original model output and prompt version. If external participants are recruited, the study will obtain the required institutional ethics approval before data collection.

\subsection{Research Questions and Reproducibility Artifacts}
The study evaluates four bounded research questions: \emph{RQ1}, whether the selected rule set detects the labelled findings in S1--S6; \emph{RQ2}, whether generated candidate paths satisfy the expected-path conditions; \emph{RQ3}, whether the heuristic ranking agrees with the pre-specified reference ranking; and \emph{RQ4}, whether LLM-assisted reports meet the reviewer rubric without unsupported or unsafe recommendations. The versioned scenario catalogue, ground-truth definitions, and validation script are maintained in the repository root under \texttt{evaluation-scenarios/}. For each executed run, the study will archive sanitised configuration snapshots, source and tool versions, normalised outputs, graph evidence, measurement records, and cleanup confirmation. Secrets, credentials, unredacted logs, and sensitive asset identifiers are excluded from the repository.

A private S5 instance, metadata-only secret, synthetic S3 object, subnet, security group, and instance profile were temporarily deployed for measurement and then removed by Terraform. The resource identifiers, execution artifacts, and account-specific logs are retained outside the repository; only sanitised evidence is archived.

Read-only AWS API checks verified the state in Table~\ref{tab:baseline}, and a subsequent Terraform plan reported no pending resource changes. The baseline pass produced one medium-severity configuration finding for the security-group ingress rule that permits \texttt{0.0.0.0/0} as a source. It produced no candidate path: the required preconditions---an Internet gateway, subnet, and network interface attached to the group---were all absent. A separate temporary S1/S2 configuration pass disabled the bucket-level S3 public-access blocks and changed the test role to \texttt{s3:*} on the empty test bucket. The evaluator detected both high-severity configuration conditions and still produced no candidate path. The intended S1 public \texttt{GetObject} policy was rejected by an account-level S3 Block Public Access safeguard; no object, public policy, or public data was created. Terraform then restored all four bucket public-access blocks and the role's \texttt{ListBucket}/\texttt{GetObject}-only policy. For S4, a separate dedicated test trail was created in the disabled state; its \texttt{IsLogging} status was false, while its private log bucket retained all public-access blocks and AES-256 default encryption. No existing trail was stopped or modified, and the dedicated trail was never enabled. The S5 pass observed the private instance-profile relationship to the synthetic object and metadata-only secret, while confirming no public address, no ingress or egress, no Internet or NAT route, IMDSv2 with hop limit one, and no \texttt{GetSecretValue} permission. It therefore asserted no candidate path, after which Terraform removed all S5-only resources and restored the role policy. These passes demonstrate bounded evidence collection and precondition rejection, not aggregate S1--S6 detection accuracy, candidate-path quality, timing, baseline-tool comparison, or LLM-report quality. The deterministic local S6 model likewise rejected the hypothetical path with no AWS or network access; it is not a deployed-service experiment.

\section{Discussion and Limitations}
The proposed framework does not establish that a graph path is exploitable merely because related resources are connected. The threat model, evidence sources, path-validity rules, and score weights must be explicit. The controlled scenarios also do not represent all production environments, cloud providers, threat actors, or organisational policies \cite{liu2024misconfigurations,rahman2019icsesmells}. The initial scope is AWS only, and the in-memory graph design may not scale to ultra-large deployments without distributed graph partitioning \cite{sabur2022scalable}.

Furthermore, while continuous auditing architectures \cite{torkura2021multicloud} and multi-cloud federations \cite{saxena2021multicloud} are increasingly common in enterprise practice, expanding cross-provider semantics remains future work. The LLM component adds cost, latency, privacy, and reliability concerns. It must not receive unapproved sensitive data, and its recommendations must not be executed automatically. These limitations motivate a staged evaluation in which each contribution is tied to an implementation artifact, metric, evidence source, and stated limitation.

\section{Conclusion}
This paper presented CloudSentinel AI, a proposed framework for combining AWS configuration assessment, knowledge-graph modeling, candidate attack-path analysis, contextual prioritisation, and LLM-assisted reporting. The central contribution is a reproducible evaluation design that separates labelled finding detection, candidate-path validity, prioritisation, and explanation quality. Future work will integrate the read-only evidence collector into the product pipeline, complete the remaining rule implementations and any separately approved S6 private instrumentation, archive sanitised evidence, and report bounded results without generalising beyond the evaluated configurations.
