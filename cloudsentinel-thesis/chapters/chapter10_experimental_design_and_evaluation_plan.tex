\section{Chapter 10 Experimental Design and Evaluation Plan}

\subsection{10.1 Introduction}

This chapter presents the experimental design and evaluation methodology proposed for validating the effectiveness of the CloudSentinel AI framework. The objective of the experimental evaluation is to determine whether the proposed framework improves cloud security assessment when compared with existing Cloud Security Posture Management (CSPM) solutions. The evaluation focuses on four key aspects:

\begin{itemize}
\tightlist
\item
  Accuracy of cloud misconfiguration detection\\
\item
  Identification of multi-stage attack paths\\
\item
  Effectiveness of context-aware risk prioritization\\
\item
  Quality and usefulness of AI-generated security explanations
\end{itemize}

\subsection{10.2 Experimental Objectives}

The experiments are designed to evaluate the proposed framework against predefined research objectives.

\begin{itemize}
\tightlist
\item
  \textbf{Objective 1:} Evaluate the ability of CloudSentinel AI to identify cloud misconfigurations across AWS resources.\\
\item
  \textbf{Objective 2:} Measure the framework's capability to generate realistic attack paths by correlating multiple cloud resources.\\
\item
  \textbf{Objective 3:} Assess the effectiveness of contextual risk scoring compared to static severity classifications.\\
\item
  \textbf{Objective 4:} Evaluate the quality and interpretability of AI-generated security explanations.\\
\item
  \textbf{Objective 5:} Compare the overall performance of CloudSentinel AI with selected baseline cloud security tools.
\end{itemize}

\subsection{10.4 Experimental Scenarios}

To evaluate the framework under realistic conditions, several cloud environments with intentionally introduced security weaknesses will be created.

\begin{itemize}
\tightlist
\item
  \textbf{Scenario 1 -- Public Storage Exposure:} Amazon S3 buckets will be configured with public read or write permissions. Expected Outcome: Detect public bucket, sensitive data exposure, business impact, and remediation recommendation.\\
\item
  \textbf{Scenario 2 -- Overly Permissive IAM Policies:} IAM users and roles will be assigned excessive administrative privileges. Expected Outcome: Identify privilege escalation risks, excessive permissions, and potential attack paths.\\
\item
  \textbf{Scenario 3 -- Insecure Network Configuration:} Security Groups will intentionally expose SSH and RDP ports to the Internet. Expected Outcome: Detect internet-facing resources, network exposure, and possible attack chains.\\
\item
  \textbf{Scenario 4 -- Disabled Logging:} AWS CloudTrail logging will be disabled. Expected Outcome: Identify reduced visibility, explain the impact on forensic investigations, and recommend enabling centralized logging.\\
\item
  \textbf{Scenario 5 -- Multi-Stage Candidate Path:} A controlled test case will combine an EC2 workload, a restricted test security group, a deliberately over-permissive test IAM role, test-only Secrets Manager access, and a non-sensitive S3 bucket. Expected Outcome: Generate and document a candidate path with the evidence and preconditions required at each step; it will not be presented as proof of exploitation.\\
\item
  \textbf{Scenario 6 -- SSRF-to-IAM Credential-Access Candidate Path:} A deliberately instrumented, non-production test service will simulate application-to-metadata access in an isolated account. No real sensitive data, production credentials, or public exposure will be used. Expected Outcome: Identify the configuration and identity preconditions required for a candidate SSRF-to-IAM credential-access path, or document why the path is invalid.
\end{itemize}

\subsection{10.6 Evaluation Units and Metrics}

The proposed evaluation separates findings, candidate paths, and explanations rather than treating them as one accuracy measure. A \emph{finding} is one rule violation attached to an AWS resource. A \emph{candidate path} is one ordered sequence of graph edges with documented preconditions. A \emph{consolidated alert} is one grouped report representing one or more related findings associated with the same candidate path or asset context. The evaluation will state which unit applies to every reported metric.

For finding-level detection, true positives, false positives, true negatives, and false negatives will be determined against a scenario-specific ground-truth catalogue. Precision, recall, and F1 will apply only to this labelled finding set. Candidate-path assessment will use an independently reviewed expected-path catalogue and will report exact matches, partial matches, and invalid paths separately. Prioritisation will be evaluated against a pre-defined expert or rule-based reference ranking. Alert reduction, if measured, will use the number of consolidated alerts divided by the number of normalised baseline findings for the same scenario and configuration.

The proposed framework will be assessed using quantitative and qualitative evaluation metrics.

\subsection{10.7 AWS Safety, Cost, and Cleanup Protocol}

All future experiments will run only in isolated, authorised, non-production AWS account(s). Test roles will follow least privilege, all data will be synthetic or non-sensitive, and every experimental resource will carry project and owner tags. Budget alarms, service quotas, and a written teardown checklist will be configured before deployment. Intentionally weak configurations will remain inside the defined laboratory boundary and will not be exposed to the public Internet. The researcher will record creation and cleanup dates, verify deletion of all resources, and retain no credentials or sensitive outputs in the thesis repository.

\subsection{10.8 Experimental Workflow}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Deploy the AWS test environment with predefined configurations.\\
\item
  Introduce controlled cloud misconfigurations for each experimental scenario.\\
\item
  Execute CloudSentinel AI to collect cloud assets and identify security issues.\\
\item
  Construct the knowledge graph representing cloud resources and their relationships.\\
\item
  Generate attack paths based on graph traversal and detected vulnerabilities.\\
\item
  Calculate contextual risk scores for each attack path.\\
\item
  Generate AI-assisted explanations and remediation recommendations.\\
\item
  Execute baseline tools under identical conditions.\\
\item
  Compare results using the selected evaluation metrics.\\
\item
  Analyze the findings and summarize the performance of the proposed framework.
\end{enumerate}

\subsection{10.9 Data Analysis Strategy}

The collected experimental data will be analyzed using descriptive statistics and comparative analysis. This includes comparison of detection rates, attack path identification, contextual risk prioritization effectiveness, execution times, and usefulness of AI-generated explanations.

\subsection{10.10 Threats to Validity}

\begin{itemize}
\tightlist
\item
  \textbf{Internal Validity:} Test environments may not represent every real-world AWS deployment.\\
\item
  \textbf{External Validity:} The initial implementation focuses on AWS; results may differ for Azure, Google Cloud Platform, or hybrid environments.\\
\item
  \textbf{Construct Validity:} Risk scores depend on the contextual factors selected for evaluation.\\
\item
  \textbf{Conclusion Validity:} Performance measurements may vary with hardware specifications, cloud environment size, and network conditions.
\end{itemize}

\subsection{10.11 Expected Outcomes and Boundaries}

The planned evaluation will determine whether the proposed framework detects the labelled test findings, generates candidate paths consistent with documented preconditions, and produces advisory explanations that reviewers judge against a stated rubric. It will not, without further real-world evidence, establish general production accuracy, operational alert reduction, or superiority over all CSPM tools.

\subsection{10.12 Chapter Summary}

This chapter presented the proposed experimental design and evaluation plan for CloudSentinel AI. It defined the environment, controlled scenarios, baseline-comparison conditions, evaluation units, metrics, workflow, safety controls, analysis strategy, and threats to validity. Any future conclusions will remain bounded by the recorded scenario catalogue and experimental configuration.
